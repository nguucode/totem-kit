# Typography

Type is **role-based**: you pick `text-heading-lg` or `text-body`, not a
size. Each role carries its size, line height and weight together, so a
heading cannot end up at body weight or a body line height by omission.

The alternative — a purely dimensional scale, where `text-2xl` says how
big and never what it is for — is still available underneath. The roles
are what components use.

## The typeface

`--font-sans` leads with **`system-ui`**:

```css
system-ui, -apple-system, 'Segoe UI', Roboto, 'Helvetica Neue', Arial,
sans-serif, 'Apple Color Emoji', 'Segoe UI Emoji'
```

`system-ui` is the standards-track keyword, and it resolves to the
platform's **UI** face — San Francisco on Apple platforms, Segoe UI
Variable on Windows, Roboto on Android — which is the face those platforms
use for their own controls. Everything after it is a fallback for browsers
that do not support the keyword.

<Canvas of={TypographyStories.Families} />

**The known caveat.** On some Linux and older Android configurations
`system-ui` resolves through fontconfig to whatever is aliased as the
system font, which has historically produced a serif, or a
missing-glyph fallback for non-Latin text. The rest of the stack does not
rescue it, because the keyword *did* resolve — just badly. This is the
reason some systems leave `system-ui` out of the stack entirely. If you
ship to those platforms and see the wrong face, drop it from the front;
nothing else in the kit depends on it.

Nothing is downloaded, so the kit renders in a different face on every
platform by design. That is the right default for product UI and the wrong
one for a brand with its own type — see **Customization** below.

## Headings

Seven steps, all bold. The line height tightens as the size grows, which
is the thing a single ratio applied across a whole scale gets wrong.

<Canvas of={TypographyStories.Headings} />

| Role | Size | Line height |
| --- | --- | --- |
| `text-heading-2xl` | 2rem / 32px | 36px |
| `text-heading-xl` | 1.75rem / 28px | 32px |
| `text-heading-lg` | 1.5rem / 24px | 28px |
| `text-heading-md` | 1.25rem / 20px | 24px |
| `text-heading-sm` | 1rem / 16px | 20px |
| `text-heading-xs` | 0.875rem / 14px | 20px |
| `text-heading-2xs` | 0.75rem / 12px | 16px |

Note that headings go *below* body size: `text-heading-2xs` is 12px. Those
bottom steps are for labels and section eyebrows — a heading role is about
the semantic weight of the text, not about being large.

## Body

Three steps. `text-body` is the default at 14px — one step down from the
16px a lot of interfaces start at, which is deliberate for dense product
UI and worth knowing before you reach for it in long-form content.

<Canvas of={TypographyStories.Body} />

| Role | Size | Line height |
| --- | --- | --- |
| `text-body-lg` | 1rem / 16px | 24px |
| `text-body` | 0.875rem / 14px | 20px |
| `text-body-sm` | 0.75rem / 12px | 16px |

**Every component uses these.** Button, the field label, the input itself,
and the helper and error text are all `text-body`; only the large Button
steps up to `text-body-lg`.

## Weights

Four. Anything outside this set is not part of the system.

<Canvas of={TypographyStories.Weights} />

| Utility | Value |
| --- | --- |
| `font-normal` | 400 |
| `font-medium` | 500 |
| `font-semibold` | 600 |
| `font-bold` | 700 |

**A weight utility always beats the role.** The role's weight compiles to
`font-weight: var(--tw-font-weight, 700)` and the `font-*` utilities set
that variable — so the role's value is a fallback, not a rule, and
overriding it does not depend on class order. That is why Button can be
`text-body font-medium` without the 400 in `text-body` fighting it.

With a system stack, the weight you ask for is not guaranteed to be a
drawn face: where one is missing the browser synthesises it, and
synthesised weights look noticeably worse. 400 and 500 are safe
everywhere; verify 600 on the platforms you support.

## Scaling

Every size above is `calc(<base> * var(--scaling))`, so the
[`scaling`](?path=/docs/foundations-overview--docs) setting moves type and
spacing together. Line heights are stored as *ratios* — `calc(20 / 14)`
rather than `1.25rem` — so they follow the font size instead of having to
be rescaled themselves.

## What is not here

**A metric role for large figures.** Its sizes would be identical to three
of the heading steps; the real difference is tabular figures, which the
`tabular-nums` utility already covers. There is no stat component yet, so
it would be a role nothing reads.

**A code role.** Same size as `text-body-sm`, differing only by family.
`font-mono` covers it until a Code component exists.

**The dimensional scale is still there.** `text-xs` through `text-6xl`
exist and still scale. Prefer a role in component code; reach for a raw
size for one-off display type that no role describes.

## Customization

The family is a theme key like any other:

```css
@theme {
  --font-sans: 'Inter Variable', system-ui, sans-serif;
}
```

Every `font-sans` utility and the default body text pick it up with no
component change. Re-check the weights when you do — a real typeface
usually ships fewer weights than the four above, or different ones.

To move the scale itself rather than the face, override the role tokens
directly; each is `--text-<role>` plus its `--line-height` and
`--font-weight` companions.
