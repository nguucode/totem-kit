# Foundations

Foundations are the decisions every component inherits: color, type,
spacing, radius, elevation, cursors, and the breakpoints layouts respond
to. They live in **one file** — `src/tokens.css` — as CSS custom
properties.

There is no JavaScript theme object and no `ThemeProvider` that owns
values. A token is a CSS variable, which means the platform already knows
how to scope it, cascade it, inherit it and override it. Everything on
this page follows from that.

`tokens.css` is itself generated — see [Where the values come
from](#where-the-values-come-from) — but nothing downstream of it is.
**You** consume a plain stylesheet with no build step of your own.

## The three layers

| Layer | Where | Example |
| --- | --- | --- |
| Raw value | `:root` / `.dark` in `tokens.css` | `--primary: oklch(51.1% 0.262 276.966)` |
| Derived value | the `*` block in `tokens.css` | `--radius-control: max(…)` |
| Usage | a component's `.module.css` | `background: var(--primary)` |

Components only ever read the variable. That is what makes a rebrand a
change to one file, and what keeps theme conditionals out of component CSS
entirely — the value behind `var(--primary)` changes, the rule does not.

The derived layer is on `*` rather than `:root` on purpose: a custom
property that reads another one resolves where it is *declared*, so
putting these at the root would freeze them there and a `Theme` further
down the tree could not move them.

## Where the values come from

`tokens.css` is not written by hand. The source is a set of JSON files in
the [W3C design-token format](https://tr.designtokens.org/format/), and a
generator turns them into the stylesheet, the `Theme` component's list of
palettes, the swatches on the **Color** page, and an export for design
tools — four artefacts that used to be four chances to disagree with each
other.

Two things follow from that, and both are visible on other pages here.

**Nothing semantic holds a literal.** In the source, `primary` is
`{accent.solid}` and `foreground` is `{gray.950}` — references, not
colours. Swapping a ramp moves everything downstream of it in one edit,
which is what makes the 17 accents and 9 grays on this page a
three-line change rather than a rewrite.

**The contrast numbers are measured, not claimed.** For each of the 17
accents the generator converts the ramp through OKLCH → sRGB → relative
luminance, computes the contrast of each candidate step against a white
and a black label, and takes the first that clears 4.5:1. The focus ring
is a separate measurement against the page at 3:1. The lowest passing
accent in the current set sits at **4.56:1** — close enough to the floor
that guessing would have missed it.

Edit a ramp so that no step can carry a readable label and the build
stops with the hue named. The accessibility claims on the
[Color](?path=/docs/foundations-colors--docs) page are therefore checks,
not documentation.

## Theming

Overriding tokens globally is just CSS — redeclare them after Zweihänder's
stylesheet loads:

```css
:root {
  --radius: 1rem;
  --primary: oklch(0.55 0.2 264);
}
```

For anything narrower than the whole document, use `Theme`. It is a thin
wrapper that applies an appearance class and writes token overrides as
inline custom properties on one element, so everything inside it resolves
against those values.

```tsx
import { Theme } from 'zweihander/theme'

<Theme accentColor="violet" grayColor="slate" appearance="dark" radius="large" scaling="105%">
  <Button>Inside a violet, slate, dark, rounder, roomier scope</Button>
</Theme>
```

Five settings, each independent:

| Prop | Values |
| --- | --- |
| `accentColor` | 17 hues — drives `--primary` and `--ring` |
| `grayColor` | 9 neutral ramps — drives backgrounds, text, borders |
| `appearance` | `light`, `dark`, `inherit` |
| `radius` | `none`, `small`, `medium`, `large`, `full` |
| `scaling` | `90%` … `110%` — spacing and type together |

### Accent color

The brand hue. Seventeen, all of them measured: the solid step and the
label colour are chosen per hue so every accent clears 4.5:1 for its own
label, which is why the warm hues below carry dark labels and the cool
ones carry white. The focus ring uses a step darker than the fill, because
the lighter solids miss the 3:1 a focus indicator needs.

<Canvas of={OverviewStories.AccentColor} />

**`accentColor` sets `--primary`, not `--accent`.** The token named
`--accent` is a subtle hover surface — a different thing that happens to
share the word.

### Gray color

The neutral ramp behind surfaces, text, borders and muted fills. The
differences are subtle and cumulative; they read most clearly in dark
mode, which is how they are shown here.

<Canvas of={OverviewStories.GrayColor} />

### Scaling

One multiplier over both spacing and the type scale, so density is a
single setting rather than a per-component decision. Line heights are
unitless ratios and follow the font size on their own.

<Canvas of={OverviewStories.Scaling} />

Note that control heights scale too — at `90%` the default control is
36px, which is getting close to the floor for a touch target.

### Token overrides

`tokens` takes any custom property, with or without the `--` prefix. It is
not limited to tokens Zweihänder defines — the component writes whatever
you pass onto the element, so a token your own components read works the
same way.

<Canvas of={OverviewStories.TokenOverride} />

Overrides cascade, so a nested `Theme` inherits what it does not restate.
Because they are inline styles they also beat any stylesheet rule, which
is what makes a scoped override reliable — and what makes `Theme` the
wrong tool for setting global defaults. Use CSS for those.

### Nesting

Scopes nest in either direction: a dark panel on a light page, or a light
island inside a dark one.

<Canvas of={OverviewStories.Nested} />

The light island works because `tokens.css` declares the light values on
`:root, .light`, not on `:root` alone. `.dark` is declared afterwards at
equal specificity, so the nearer scope's class is what an element inside
it resolves against.

**One caveat.** If your own CSS branches on theme with a descendant
selector — `.dark .thing { … }` — that selector still matches inside a
light island nested in a dark ancestor, and will style it as dark. Zweihänder
Kit's own CSS never branches on theme, so it is unaffected. Read the
tokens instead of matching on `.dark` and the problem does not arise.

## Installing

Both distribution paths carry the same tokens. Copy-source drops the
component's own source into your repo and merges these values into your
stylesheet; the npm package ships them as `zweihander/tokens.css`, which
you import after your base stylesheet.

The exact commands for either are in the
[repo README](https://github.com/nguucode/zweihander).
