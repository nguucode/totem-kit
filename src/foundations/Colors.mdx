# Colors

Every color in the system is a CSS custom property declared in
`src/tokens.css`, with a counterpart under the `.dark` class. There is no
separate dark palette file and no JS theme object — one stylesheet holds
both modes.

**Read them with `var()`** — `background: var(--card)`,
`color: var(--muted-foreground)`, `border-color: var(--border)`. Because
the variable changes rather than the rule, a component written this way
switches theme without a single conditional: there is no light branch and
no dark branch anywhere in the kit's CSS.

**The swatches below read their values out of the live document**, so a
color shown here is the value the components actually get. The token
*names* are still listed by hand in `Colors.stories.tsx`, though — add a
token to `tokens.css` and it will not appear here until it is added there
too.

## Surfaces

`--background` is the page. `--card` and `--popover` are surfaces that sit
a level above it — a card inset in the page, a menu floating over it. In
light mode all three are pure white and only their foregrounds carry
meaning; in dark mode they separate, with `--background` at the darkest
step and card/popover lifted one step toward the viewer.

Each surface has a `-foreground` partner, and the pair is the contract:
put `--card-foreground` on `--card`, never `--foreground`, even where the
two happen to be equal today.

## Subtle surfaces

`--muted` and `--accent` are the same value in both modes and differ only
in intent. `--muted` is for surfaces that recede — a disabled field's
fill, a table's zebra stripe — and is the only one of the two with a
foreground meant for *long-form* secondary text. `--accent` is for
surfaces that are reacting to the user: hover on a menu item, the
selected row in a list.

They are interchangeable in appearance, so nothing breaks visually if you
swap them, and nothing tells you that you did. The distinction is the
whole point: when a brand color eventually replaces one of them, only the
intent that should change will change.

## Solid actions

Filled controls. `--primary` is the default button and **the brand hue** —
indigo out of the box, and the one token the
[`accentColor`](?path=/docs/foundations-overview--docs) setting moves. It
lightens in dark mode rather than darkening, so `--primary-foreground`
inverts with it.

`--destructive` is a hue too, but a fixed one: it stays red whatever the
accent is. A status colour that follows the brand stops being a status —
if the accent is already red, distinguish destructive actions by wording
and placement, not by colour alone.

A note on names: the token called `--accent` is **not** the brand hue. It
is a subtle surface (hover, selected row). The brand hue is `--primary`.
The collision is unfortunate and predates this kit — the names come from
the token contract the registry is compatible with.

## Lines and focus

`--border` is a divider or a container edge, `--input` is a form control's
edge, `--ring` is the focus indicator. None of them take a foreground —
they are only ever an outline color, never a fill behind text.

`--border` and `--input` are the same value in both modes and, like
muted/accent, are separated by intent rather than appearance. In dark mode
they stop being opaque neutrals and become white at 10% and 15% alpha
respectively, so an edge reads consistently whether it sits on
`--background` or on a lifted `--card`. That is the one place the palette
uses transparency.

## Dark mode

Every token on this page has a counterpart under `.dark`, switched by a
class rather than a media query, and dark is not a mechanical inversion of
light — surfaces go *up* rather than down, and strong fills get lighter so
their foregrounds flip to dark text. The Light/Dark columns in the
contrast table below cover both.

The mechanism, the three places an inversion would have gone wrong, and
how to follow the OS setting are on their own page:
**[Dark mode](?path=/docs/foundations-dark-mode--docs)**.

## Contrast

Measured, not assumed — every pair below is computed from the OKLCH
values in `tokens.css`. WCAG AA wants 4.5:1 for body text and 3:1 for UI
component boundaries such as a focus ring.

| Pair | Light | Dark |
| --- | --- | --- |
| `background` / `foreground` | 19.79:1 | 18.96:1 |
| `card` / `card-foreground` | 19.79:1 | 17.16:1 |
| `popover` / `popover-foreground` | 19.79:1 | 17.16:1 |
| `primary` / `primary-foreground` | 6.17:1 | 5.74:1 |
| `secondary` / `secondary-foreground` | 16.42:1 | 14.48:1 |
| `accent` / `accent-foreground` | 16.42:1 | 14.48:1 |
| `destructive` / `destructive-foreground` | 4.56:1 | 6.19:1 |
| `muted` / `muted-foreground` | **4.34:1** | 5.83:1 |
| `background` / `muted-foreground` | 4.73:1 | 7.63:1 |
| `background` / `ring` | 8.07:1 | 6.34:1 |

The `primary` row is the default indigo accent. Every one of the seventeen
accents is measured the same way and clears 4.5:1 for its own label — see
[Overview → Accent color](?path=/docs/foundations-overview--docs).

**`--muted-foreground` on `--muted` is 4.34:1 in light mode, under AA.**
On the page background — where secondary text usually lives — the same
token is 4.73:1 and passes. Muted text on a muted fill is the combination
to avoid; if you need it, darken `--muted-foreground` to neutral-600
(7.15:1 on muted) and accept that all secondary text in the kit gets
heavier.

**Two values are deliberately off the beaten path.** `--ring` follows the
accent at its `-700` step rather than being a neutral, because a focus
indicator has to clear 3:1 against the page under WCAG 1.4.11 and the
lighter solids miss it — yellow-600 measures 2.93:1, so the ring uses a
step darker than the fill for every accent.
And dark `--destructive-foreground` is neutral-900 rather than near-white:
dark mode inverts the destructive fill to red-400, and near-white on
red-400 is 2.77:1, which makes the label of a destructive button in dark
mode fail AA outright.

## Color is never the only signal

`--destructive` on a button does not say what will be destroyed, and a red
badge means nothing to a reader who cannot distinguish it from a neutral
one. Pair color with words, an icon, or a shape every time it carries
meaning. The contrast numbers above are a floor, not a design review.

## Where the values come from

**Every value is a step off a published ramp, digit for digit.** Nothing
here was hand-picked or eyeballed. Two ramps feed the palette and each is
swappable on its own: an **accent** (indigo by default) for `--primary` and
`--ring`, and a **gray** (neutral by default) for everything structural.

| Token | Light | Dark | Driven by |
| --- | --- | --- | --- |
| `background` | white | gray-950 | gray |
| `foreground` | gray-950 | gray-50 | gray |
| `card`, `popover` | white | gray-900 | gray |
| `card-foreground`, `popover-foreground` | gray-950 | gray-50 | gray |
| `primary` | accent-600 | accent-400 | **accent** |
| `primary-foreground` | white or near-black | near-black | **accent** |
| `secondary`, `muted`, `accent` | gray-100 | gray-800 | gray |
| `secondary-foreground`, `accent-foreground` | gray-900 | gray-50 | gray |
| `muted-foreground` | gray-500 | gray-400 | gray |
| `destructive` | red-600 | red-400 | fixed |
| `destructive-foreground` | neutral-50 | neutral-900 | fixed |
| `border`, `input` | gray-200 | white 10% / 15% | gray |
| `ring` | accent-700 | accent-400 | **accent** |

The light accent step is `-600` for most hues but `-700` for sky, fuchsia,
pink and rose, and the label is white or near-black depending on which one
clears 4.5:1 on that fill — the warm hues take dark labels. Exceptions to
the ramp rule: light `--background` (pure white, not gray-50) and dark
`--border`/`--input` (alpha, so edges work over any surface).

`--destructive` deliberately does **not** follow the accent. A status
colour that changes with the brand stops being a status.

## Naming

Token names describe a **role**, not a property or a color. `--primary` is
not "the brand color" and `--destructive` is not "red"; they are the
default action and the dangerous one. The names are also the common
contract most token-based kits share, which is what lets a component
copied out of Zweihänder resolve against tokens a target project already
has instead of arriving with its own private palette.

Figma, by contrast, conventionally names tokens by property —
`bg/primary`, `text/primary`, `border/default`. Those do not map one to
one: Figma's `text/primary` is this system's `--foreground`, and its
`bg/primary` is `--background`. Neither is `--primary`. Worth pinning down
before any Figma sync, since the collision is silent.

## Primitives

The full underlying palette — 22 hues × 11 shades. None of these
classes are referenced anywhere in the kit, so they are force-generated by
an `@source inline(...)` directive in `src/index.css` purely so this page
can render them.

This is raw material, not a palette to build UI from. Reach for a
primitive when you are defining the *next* semantic token; if a primitive
shows up in a component, a token is missing.

## Customization

Swap the raw values in `:root` and `.dark` in `src/tokens.css`. Nothing
that reads `var(--primary)` or `var(--muted-foreground)` changes, because
every rule points at the variable rather than the value.

Two things to carry through a rebrand: re-measure the pairs in the
contrast table — a brand hue at the same *lightness* as neutral-900 will
not necessarily hit the same ratios — and keep light and dark as separate
decisions. Lifting a brand color for dark mode by reusing the light value
is what produces the 2.77:1 failure documented above.

Projects that install through the registry get these values merged into
their own stylesheet; projects on the npm package import
`zweihander/tokens.css` and override afterwards.
