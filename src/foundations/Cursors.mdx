# Cursors

Two tokens, and a convention that surprises most people: **buttons do not
get `cursor: pointer`.**

## The convention

`cursor: pointer` means "this navigates" — it is the hand that appears
over a link. Browsers have never applied it to `<button>`, `<select>` or a
checkbox, and neither does this kit. Interactive elements that act on the
current page keep the regular arrow; only a link gets the hand. This is
a deliberate departure from the very common `button { cursor: pointer }`
reset.

It is worth knowing the argument on the other side: a large body of
usability opinion holds that the hand cursor is now such a widespread
affordance for "clickable" that removing it costs more than the semantic
purity gains. If your product takes that view, this is a one-line change —
see **Customization** below. The point of making it a token is that it is
one line, in one place, rather than a decision re-litigated per component.

## `--cursor-button`

`default` — the regular arrow. Applied by Button via
`cursor-(--cursor-button)`.

Note this changes nothing visually today: a native `<button>` already
shows the arrow. **The token's job is not its current value; it is that
the value is reachable.** Without it, switching the kit to `pointer` means
editing every component; with it, it is one declaration in `tokens.css`.

## `--cursor-disabled`

`not-allowed` — and **no component uses it.**

Button's disabled state is `disabled:pointer-events-none`, which makes the
element untargetable by the pointer. An untargetable element is never
hovered, so no cursor of its own can ever render on it; setting one would
be dead CSS. The `pointer-events-none` is not incidental — Button supports
`asChild`, so it can render as an `<a>`, which ignores the `disabled`
attribute entirely. Blocking pointer events is what actually disables it
in that case.

The token exists for the other pattern: a control that stays hit-testable
while disabled, typically because it is wrapped in a tooltip explaining
*why* it is disabled. That trade-off — a disabled control you can hover
and get an explanation from, versus one that is inert — is a real design
choice, and this token is for the first branch of it.

## Adding tokens

A mature system ends up with a token per interactive component —
buttons, checkboxes, links, menu items, radios, switches, slider thumbs.
This kit has two, because it has two components.

**Add a token when the component that needs it is built, not before.** A
`--cursor-slider-thumb` with no Slider is a value nobody can verify and
that the eventual Slider may not want. The two here already demonstrate
the pattern.

## Customization

Both are plain CSS keywords, not colors, so they override like any other
custom property:

```css
:root {
  --cursor-button: pointer;
}
```

Load any override after Totem Kit's own stylesheet so the cascade picks it
up. Because `--cursor-disabled` is unused, changing it has no effect until
a component consumes it.
